### 前言

從Prompt到Skill，演變到Harness，AI Agent的世界已經發生巨變。本篇記載在學習怎麼與Agent互動上讓它發揮自主監控，驗證，最後交付可執行的成果，不用人類介入，屢次debug。當然，Harness文件也需要隨之演變。

<p>
  最近讀 OpenAI 的文章《Harness 工程：在智慧體優先的世界中善用 Codex》，有些概念一開始不太好懂。

<h2>一、文章在說什麼</h2>

<p>
  <strong>實驗背景：</strong>OpenAI 團隊用 5 個月做出一個內部產品，約 100 萬行程式碼，
  <strong>沒有任何一行是人手寫的</strong>，全由 Codex 代理完成。他們估計只花了手寫所需時間的十分之一。
</p>

<p>
  <strong>什麼是 Harness？</strong>原意是「馬具、駕馭裝置」。AI 代理像一匹力氣很大的馬，
  harness 就是韁繩、鞍和跑道，讓牠往對的方向穩定地跑。
  所以 harness engineering 的重點不再是「自己寫程式」，而是<strong>設計代理工作的環境</strong>。
</p>

<h3>Harness 的四個零件</h3>

<ol>
  <li>
    <strong>知識地圖：</strong>他們試過把所有規則塞進一個巨大的 <code>AGENTS.md</code>，結果失敗：占滿上下文、很快過時。
    後來改成一份約 100 行的「目錄」，指向 <code>docs/</code> 裡的詳細文件，代理需要時再往下找。
  </li>
  <li>
    <strong>看得見的工具：</strong>讓代理能自己操作瀏覽器、查日誌和指標，這樣它能重現錯誤、驗證修正，不必等人檢查。
    有些任務單次連續跑了六小時以上。
  </li>
  <li>
    <strong>架構規則：</strong>規定程式碼只能依固定層級單向依賴，再用自訂 linter 強制執行，
    報錯訊息還寫成「該怎麼修」直接餵給代理。重點是管邊界，不管細節寫法。
  </li>
  <li>
    <strong>自動清理：</strong>代理會複製現有的壞習慣，造成程式碼漂移。他們原本每週五人工清理，
    後來改成定期跑背景代理掃描並開重構 PR，像垃圾回收一樣。
  </li>
</ol>

<h3>人類的新角色</h3>

<p>
  代理卡住時，不是叫它「再努力一點」，而是問：<strong>缺了什麼能力？</strong>然後把工具、規則或文件補進環境（圖中的回饋箭頭）。
  文中有一句話值得記住：<strong>代理在執行時看不到的東西，就等於不存在</strong>。
  所以 Slack 討論、腦中的經驗，都必須寫進程式碼庫。
</p>

<div class="hx-note">
  <strong>注意：</strong>作者也說明，這些成果高度依賴他們自己專案的結構與工具，不能直接當成通用結論；
  長期的架構一致性也還在觀察中。
</div>

<h2>二、在 Claude 上能嘗試類似做法嗎？</h2>

<p>
  可以，概念幾乎一一對應，只是名稱不同。以下以 Claude Code（在終端機或編輯器裡讓 Claude 動手改程式碼的工具）為例：
</p>

<table>
  <thead>
    <tr><th>文章做法</th><th>Claude 上的對應</th></tr>
  </thead>
  <tbody>
    <tr><td>短目錄式 <code>AGENTS.md</code></td><td>專案根目錄的 <code>CLAUDE.md</code>，保持精簡，細節放 <code>docs/</code> 再讓它引用</td></tr>
    <tr><td>可重複的流程</td><td>Skills：把常做的流程寫成說明資料夾</td></tr>
    <tr><td>看得見的工具</td><td>MCP 連接器，例如瀏覽器、資料庫、日誌工具</td></tr>
    <tr><td>自動把關</td><td>Hooks（在特定動作前後自動執行檢查）、linter、測試</td></tr>
    <tr><td>多個代理互相審查</td><td>Subagents：開一個專門審查的代理檢查另一個代理的成果</td></tr>
    <tr><td>定期清理</td><td>排程任務，或在 CI 中定時執行 Claude 做掃描</td></tr>
  </tbody>
</table>

<h2>三、怎麼建立 CLAUDE.md：實例說明</h2>

<p>
  <code>CLAUDE.md</code> 是放在專案根目錄的一份文字檔，Claude 每次開始工作時都會讀它，
  等於替代理準備的「入職說明」。原則和文章一致：<strong>短、像目錄、只放代理猜不到的事</strong>。
</p>

<h3>起手式</h3>
<p>
  在專案資料夾啟動 Claude Code 後，可以先用 <code>/init</code> 讓它掃描專案、產生第一版草稿，再由你刪減修改。
  （指令細節以官方文件為準。）
</p>

<h3>範例一：第一版（以假想的記帳 App 為例）</h3>

<pre><code># 專案：記帳 App（Next.js + TypeScript）

## 常用指令
- 安裝：npm install
- 開發：npm run dev
- 測試：npm test（改完程式碼一定要跑）
- 檢查：npm run lint

## 目錄結構
- src/app/   頁面
- src/lib/   商業邏輯（不可引用 src/app）
- docs/      詳細文件，需要時再讀

## 規則
- 使用者輸入在 src/lib/ 的邊界先驗證，再往內傳
- 不要新增套件，除非先問我
- 不要修改 migrations/ 內既有的檔案

## 完成標準
- 測試與 lint 都通過才算完成
- 回覆時列出改了哪些檔案
</code></pre>

<p>重點：只有 20 行左右，沒有長篇大論，每一條都是「看程式碼猜不出來」的資訊。</p>

<h3>範例二：用「指路」取代「塞滿」</h3>

<p>內容變多時，不要全部堆進 <code>CLAUDE.md</code>，而是讓它指向別的文件，對應文章的「漸進式揭露」：</p>

<pre><code>## 進階文件（需要時才讀）
- 資料庫設計：docs/db-schema.md
- 測試寫法與範例：docs/testing.md
- 付款流程的注意事項：docs/payments.md
</code></pre>

<h3>範例三：把錯誤變成規則（最重要的習慣）</h3>

<p>這就是文章裡「缺了什麼能力？」的實際做法。每次 Claude 做錯，修正後多問一步，把教訓寫進環境：</p>

<table>
  <thead>
    <tr><th>發生的狀況</th><th>錯誤的處理</th><th>建議的處理</th></tr>
  </thead>
  <tbody>
    <tr>
      <td>Claude 改了舊的資料庫遷移檔，造成錯誤</td>
      <td>在對話裡罵一句，下次又犯</td>
      <td>在 <code>CLAUDE.md</code> 加一條「不要修改 migrations/ 內既有檔案」，必要時用 hook 直接阻擋</td>
    </tr>
    <tr>
      <td>Claude 常忘記跑測試就說完成</td>
      <td>每次提醒</td>
      <td>在「完成標準」寫明要跑測試；再加一個自動檢查</td>
    </tr>
    <tr>
      <td>Claude 在不該引用的地方引用了模組</td>
      <td>人工逐次審查</td>
      <td>加一條 lint 規則，違反就報錯，並把「該怎麼改」寫在錯誤訊息裡</td>
    </tr>
  </tbody>
</table>

<h3>常見的寫法陷阱</h3>
<ul>
  <li>寫成百科全書：太長會擠掉真正的任務內容，重要規則反而被淹沒。</li>
  <li>寫「寫乾淨的程式碼」這類空話：代理本來就會試著這樣做，沒有提供新資訊。</li>
  <li>寫完不維護：過時的規則比沒有規則更糟，定期刪除失效的條目。</li>
  <li>能用程式強制的規則，就別只用文字拜託：測試、linter、hook 比文字說明可靠。</li>
</ul>

<h2>四、從小處開始的三步驟</h2>

<ol>
  <li>挑一個小專案，寫一份 30–50 行的 <code>CLAUDE.md</code>：目錄結構、怎麼跑測試、不能碰的地方。</li>
  <li>每次 Claude 做錯，就問「缺了什麼規則或工具？」，把答案補進 <code>CLAUDE.md</code> 或測試，而不是只在對話裡糾正。</li>
  <li>加上自動測試與 linter，讓 Claude 自己跑、自己修，這就是最小版的回饋迴路。</li>
</ol>
